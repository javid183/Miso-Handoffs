## Thread safety (AI worker)

The AI worker does reach `GetEntities()` in the editor: AI ability checks (`AbilityPreset` activation/target tag queries, `RuntimeAbility` target filter, effect `CanApply` checks) call `GTagSet.Match` -> `GTagRegistry.MatchEntry` -> `ResolveEntity`, and in the editor `ResolveEntity` already runs `RebuildHierarchyLinks()` (writes `Parent` on the registry's copies) and `BuildEntitiesRefMap()` -> `GetEntities()` on every call. In player builds neither runs per call (the map is built once in `Awake`), so the change has no effect there.

The added writes are safe on that path:
- No Unity-object API: `RebuildParentLinks` is plain C# on `[Serializable]` `GTag` objects; reading the `gTags` list field of the ScriptableObject is a plain field read (no `==` null on a UnityEngine.Object, no `gameObject`).
- Every writer writes the same value to each `Parent` (null for roots, the true parent for children), and a reference write is atomic, so a concurrent reader can only see the old value or the correct one. Since each `GetEntities` call links before it reads IDs on its own thread, its own map is always correct; the only racing outcome is the pre-existing "not yet linked" state, which the call itself then fixes.
- Concurrent `foreach` over the `List<GTag>`s is read-only (nothing mutates them at runtime; the inspector is main-thread and not during an AI turn).
- Pre-existing and unchanged: the registry swaps `EntitiesRefMap` from several threads in the editor, and `GlobalSettingsSO.GetRegistry` touches `Instance` off-thread. Not made worse; noted below.
